## 一、典型场景案例

### 场景1: 玩家断线重连

**问题描述**:
玩家在Spin过程中网络断开,重连后如何恢复状态?

**解决方案**:

```go
// 1. 玩家断线时保存状态
func (a *ActorPlayer) OnDisconnect() {
    // 保存当前状态到Redis
    state := &PlayerState{
        UserId:    a.UserId,
        Coin:      a.Coin,
        MachineId: a.Machine.Id,
        LastSpin:  a.LastSpinResult,
        Timestamp: time.Now().Unix(),
    }
    
    redis.Set(fmt.Sprintf("player:state:%d", a.UserId), state, 5*time.Minute)
}

// 2. 重连时恢复状态
func (a *ActorPlayer) OnReconnect() {
    // 从Redis恢复状态
    key := fmt.Sprintf("player:state:%d", a.UserId)
    state := &PlayerState{}
    
    if redis.Get(key, state) {
        a.Coin = state.Coin
        a.Machine = loadMachine(state.MachineId)
        
        // 如果有未完成的Spin,返回结果
        if state.LastSpin != nil {
            a.sendSpinResult(state.LastSpin)
        }
    }
}

// 3. 幂等性保证
func (a *ActorPlayer) handleSpin(req *SpinRequest) {
    // 检查是否重复请求
    if req.RequestId == a.LastRequestId {
        // 返回缓存的结果
        a.sendSpinResult(a.LastSpinResult)
        return
    }
    
    // 正常处理
    result := a.doSpin(req)
    
    // 缓存结果
    a.LastRequestId = req.RequestId
    a.LastSpinResult = result
}
```

**关键点**:
- 状态持久化(Redis)
- 幂等性设计
- 超时清理机制

### 场景2: 数据库连接池耗尽

**问题描述**:
高峰期数据库连接池耗尽,导致请求超时

**现象**:
```
Error: pq: sorry, too many clients already
Response time: 5000ms+
```

**排查过程**:

```bash
# 1. 查看数据库连接数
SELECT count(*) FROM pg_stat_activity;
# 结果: 100 (达到max_connections限制)

# 2. 查看连接来源
SELECT client_addr, count(*) 
FROM pg_stat_activity 
GROUP BY client_addr;
# 发现某个Game节点占用80个连接

# 3. 查看慢查询
SELECT query, query_start, state 
FROM pg_stat_activity 
WHERE state != 'idle' 
AND query_start < now() - interval '5 seconds';
# 发现大量SELECT查询未释放
```

**解决方案**:

```go
// 1. 优化连接池配置
db.SetMaxOpenConns(50)      // 降低最大连接数
db.SetMaxIdleConns(25)      // 增加空闲连接
db.SetConnMaxLifetime(time.Hour)  // 连接最大生命周期
db.SetConnMaxIdleTime(10 * time.Minute)  // 空闲连接超时

// 2. 使用连接池监控
go func() {
    ticker := time.NewTicker(30 * time.Second)
    for range ticker.C {
        stats := db.Stats()
        log.Infof("DB Pool: Open=%d, InUse=%d, Idle=%d, Wait=%d",
            stats.OpenConnections,
            stats.InUse,
            stats.Idle,
            stats.WaitCount,
        )
        
        // 告警
        if stats.WaitCount > 100 {
            alert("Database connection pool exhausted")
        }
    }
}()

// 3. 批量操作减少连接占用
func (s *PlayerSaver) BatchSave(players []*Player) error {
    // 使用事务批量保存
    return db.Transaction(func(tx *gorm.DB) error {
        return tx.CreateInBatches(players, 100).Error
    })
}

// 4. 读写分离
type DBManager struct {
    master *gorm.DB  // 写库
    slaves []*gorm.DB  // 读库
}

func (m *DBManager) GetReadDB() *gorm.DB {
    // 随机选择一个从库
    index := rand.Intn(len(m.slaves))
    return m.slaves[index]
}

func (m *DBManager) GetWriteDB() *gorm.DB {
    return m.master
}
```

**优化效果**:
- 连接数: 100 → 50
- 响应时间: 5000ms → 50ms
- 错误率: 5% → 0.01%

### 场景3: Actor消息积压

**问题描述**:
某个玩家Actor消息队列积压,导致响应缓慢

**现象**:
```
Player 12345: mailbox size = 10000
Response time: 3000ms
Other players: normal
```

**排查过程**:

```go
// 1. 监控Actor消息队列
func (a *ActorPlayer) monitorMailbox() {
    go func() {
        ticker := time.NewTicker(10 * time.Second)
        for range ticker.C {
            size := len(a.mailbox)
            if size > 1000 {
                log.Warnf("Player %d mailbox size: %d", a.UserId, size)
            }
        }
    }()
}

// 2. 分析消息类型
func (a *ActorPlayer) OnReceive(msg Message) {
    start := time.Now()
    defer func() {
        elapsed := time.Since(start)
        if elapsed > 100*time.Millisecond {
            log.Warnf("Slow message: route=%s, elapsed=%v", msg.Route, elapsed)
        }
    }()
    
    // 处理消息
    a.handleMessage(msg)
}
```

**根因分析**:
- Spin计算耗时过长(500ms)
- 玩家频繁点击Spin
- 消息队列积压

**解决方案**:

```go
// 方案1: 异步化耗时操作
func (a *ActorPlayer) handleSpin(req *SpinRequest) {
    // 快速返回ACK
    a.sendAck(req.RequestId)
    
    // 异步计算结果
    go func() {
        result := a.calculateSpinResult(req)
        a.sendSpinResult(result)
    }()
}

// 方案2: 限流
type RateLimiter struct {
    limiter *rate.Limiter
}

func (a *ActorPlayer) handleSpin(req *SpinRequest) {
    // 限制每秒最多2次Spin
    if !a.rateLimiter.Allow() {
        a.sendError("too many requests")
        return
    }
    
    // 正常处理
    a.doSpin(req)
}

// 方案3: 消息优先级
type PriorityMailbox struct {
    highPriority chan Message
    lowPriority  chan Message
}

func (m *PriorityMailbox) Receive() Message {
    select {
    case msg := <-m.highPriority:
        return msg
    default:
        select {
        case msg := <-m.highPriority:
            return msg
        case msg := <-m.lowPriority:
            return msg
        }
    }
}
```

**优化效果**:
- 消息队列: 10000 → 10
- 响应时间: 3000ms → 50ms
- 玩家体验: 显著提升

### 场景4: 内存泄漏

**问题描述**:
Game节点运行一段时间后内存持续增长,最终OOM

**现象**:
```
Memory: 500MB → 2GB → 4GB → OOM Killed
Goroutines: 1000 → 10000 → 50000
```

**排查过程**:

```bash
# 1. 使用pprof分析内存
go tool pprof http://localhost:6060/debug/pprof/heap

# 2. 查看内存分配
(pprof) top10
Showing nodes accounting for 1.5GB, 75% of 2GB total
      flat  flat%   sum%        cum   cum%
    500MB 25.00% 25.00%     500MB 25.00%  ActorPlayer.loadData
    300MB 15.00% 40.00%     300MB 15.00%  SpinResult.new
    200MB 10.00% 50.00%     200MB 10.00%  Timer.new

# 3. 查看goroutine泄漏
go tool pprof http://localhost:6060/debug/pprof/goroutine
(pprof) top10
Showing 50000 goroutines
```

**根因分析**:

```go
// 问题代码1: 定时器未释放
func (a *ActorPlayer) startHeartbeat() {
    ticker := time.NewTicker(30 * time.Second)
    go func() {
        for range ticker.C {
            a.sendHeartbeat()
        }
    }()
    // 问题: ticker从未Stop,goroutine泄漏
}

// 问题代码2: Actor未释放
func (m *ActorManager) GetOrCreate(userId int64) *ActorPlayer {
    actor := &ActorPlayer{UserId: userId}
    m.actors[userId] = actor
    return actor
    // 问题: 玩家下线后Actor未删除
}

// 问题代码3: 对象未归还对象池
func handleSpin() {
    result := spinResultPool.Get().(*SpinResult)
    // 使用result
    // 问题: 忘记Put回对象池
}
```

**解决方案**:

```go
// 修复1: 正确管理定时器
func (a *ActorPlayer) startHeartbeat() {
    a.ticker = time.NewTicker(30 * time.Second)
    go func() {
        for {
            select {
            case <-a.ticker.C:
                a.sendHeartbeat()
            case <-a.stopChan:
                return  // 退出goroutine
            }
        }
    }()
}

func (a *ActorPlayer) OnStop() {
    a.ticker.Stop()
    close(a.stopChan)
}

// 修复2: 玩家下线清理Actor
func (m *ActorManager) Remove(userId int64) {
    m.mu.Lock()
    defer m.mu.Unlock()
    
    if actor, exists := m.actors[userId]; exists {
        actor.OnStop()  // 清理资源
        delete(m.actors, userId)
    }
}

// 修复3: 使用defer归还对象
func handleSpin() {
    result := spinResultPool.Get().(*SpinResult)
    defer spinResultPool.Put(result)  // 确保归还
    
    // 使用result
}

// 监控goroutine数量
func monitorGoroutines() {
    ticker := time.NewTicker(1 * time.Minute)
    for range ticker.C {
        count := runtime.NumGoroutine()
        if count > 10000 {
            log.Warnf("Too many goroutines: %d", count)
            // 触发告警
        }
    }
}
```

**优化效果**:
- 内存稳定在500MB
- Goroutine数量稳定在1000
- 无OOM问题

### 场景5: 热点数据竞争

**问题描述**:
Jackpot奖池被多个玩家同时访问,出现数据竞争

**现象**:
```
Race detected: JackpotPool.TotalAmount
Expected: 1000000
Actual: 950000
Lost: 50000 (数据丢失!)
```

**解决方案**:

```go
// 方案1: 使用互斥锁
type JackpotPool struct {
    mu          sync.Mutex
    TotalAmount int64
}

func (j *JackpotPool) Add(amount int64) {
    j.mu.Lock()
    defer j.mu.Unlock()
    j.TotalAmount += amount
}

// 方案2: 使用原子操作
type JackpotPool struct {
    TotalAmount int64  // 使用atomic操作
}

func (j *JackpotPool) Add(amount int64) {
    atomic.AddInt64(&j.TotalAmount, amount)
}

func (j *JackpotPool) Get() int64 {
    return atomic.LoadInt64(&j.TotalAmount)
}

// 方案3: 使用Actor模型
type JackpotActor struct {
    cherry.ActorBase
    TotalAmount int64
}

func (j *JackpotActor) OnReceive(msg Message) {
    switch msg.Type {
    case "add":
        j.TotalAmount += msg.Amount
    case "trigger":
        if j.shouldTrigger() {
            j.TotalAmount = 0
            j.sendJackpot(msg.PlayerId)
        }
    }
}

// 所有操作通过消息发送
jackpotActor.Send(Message{Type: "add", Amount: 100})
```

**问题**: 玩家登录查询慢(500ms)

-- 优化前

EXPLAIN ANALYZE SELECT * FROM players WHERE user_id = 12345;

### 优化2: 缓存策略

**问题**: 机台配置频繁查询数据库

```go
// 优化前: 每次Spin都查询
func (a *ActorPlayer) handleSpin() {
    config := db.GetMachineConfig(a.MachineId)  // 每次查DB
    result := calculateResult(config)
}

// 优化后: 多级缓存
type ConfigCache struct {
    // L1: 本地内存缓存
    local map[int32]*MachineConfig
    localMu sync.RWMutex
    
    // L2: Redis缓存
    redis *redis.Client
}

func (c *ConfigCache) Get(machineId int32) *MachineConfig {
    // 1. 查本地缓存
    c.localMu.RLock()
    if config, exists := c.local[machineId]; exists {
        c.localMu.RUnlock()
        return config
    }
    c.localMu.RUnlock()
    
    // 2. 查Redis
    key := fmt.Sprintf("machine:config:%d", machineId)
    config := &MachineConfig{}
    if c.redis.Get(key, config) == nil {
        // 更新本地缓存
        c.localMu.Lock()
        c.local[machineId] = config
        c.localMu.Unlock()
        return config
    }
    
    // 3. 查数据库
    config = db.GetMachineConfig(machineId)
    
    // 4. 回写缓存
    c.redis.Set(key, config, time.Hour)
    c.localMu.Lock()
    c.local[machineId] = config
    c.localMu.Unlock()
    
    return config
}
```

**优化效果**:
- 数据库QPS: 10000 → 10
- 响应时间: 50ms → 5ms
- 缓存命中率: 99.9%

## 三、故障处理案例

### 案例1: 数据库主从延迟

**故障现象**:
玩家充值后余额未更新

**排查**:
```bash
# 检查主从延迟
SELECT now() - pg_last_xact_replay_timestamp() AS replication_delay;
# 结果: 30 seconds (延迟30秒!)
```

**临时方案**:
```go
// 充值等关键操作强制读主库
func (p *Player) Recharge(amount int64) {
    // 写主库
    masterDB.Model(&Player{}).
        Where("user_id = ?", p.UserId).
        Update("coin", gorm.Expr("coin + ?", amount))
    
    // 读主库(避免读从库看到旧数据)
    masterDB.First(&p, p.UserId)
}
```

**根本解决**:
- 优化主从同步配置
- 增加从库数量
- 使用同步复制

### 案例2: NATS消息丢失

**故障现象**:
RPC调用偶尔超时,消息丢失

**排查**:
```bash
# 检查NATS状态
nats-server -m 8222
curl http://localhost:8222/varz
# slow_consumers: 5 (有慢消费者!)
```

**解决**:
```go
// 1. 增加消息确认
nc.Subscribe("game.rpc", func(msg *nats.Msg) {
    defer msg.Ack()  // 确认消息
    handleRPC(msg)
})

// 2. 设置重试
nc.QueueSubscribe("game.rpc", "workers", func(msg *nats.Msg) {
    if err := handleRPC(msg); err != nil {
        msg.Nak()  // 重新投递
    } else {
        msg.Ack()
    }
})

// 3. 监控消息队列
go func() {
    ticker := time.NewTicker(30 * time.Second)
    for range ticker.C {
        stats := nc.Stats()
        if stats.PendingMsgs > 1000 {
            log.Warn("Too many pending messages")
        }
    }
}()
```
