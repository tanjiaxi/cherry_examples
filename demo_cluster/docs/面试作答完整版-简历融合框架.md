**一句话结论：** 我做的是面向海外市场的高并发游戏后端，核心是 Go + Actor 并发模型 + NATS 消息，后期把部分服务迁到了 AWS Serverless。

2. **架构关键点：**
   "业务逻辑用的是 Actor 并发模型，简单说就是每个玩家的数据由专门的一个 Actor 串行处理，这样不用加很多锁，也不会互相打架。"

3. **后来的演进（重点，带数字）：**
   "跑了一段时间之后，为了应对游戏高峰期的突发流量，我们把一部分 Golang 分布式服务改造成了 AWS Serverless 架构，用 Lambda、DynamoDB、PostgreSQL、Redis 这些。改完之后请求峰值能扛到 10000 QPS，配合 CloudFront 和日志系统，可用性做到了 99.98%。"

4. **收尾（给面试官一个抓手，方便他往下问）：**
   "这个项目里我主要负责两块：一块是消息可靠性和数据一致性，比如 Spin 接口和活动接口用消息队列加 Outbox 模式对齐数据；另一块是性能和可观测性，比如接口延迟优化、日志分析平台这些。"

> **为什么这么组织：** 先说"是什么"（低门槛，面试官容易跟上），再说"关键技术选型"（体现你懂架构），再抛数字（证明规模真实），最后主动给两个可以深挖的方向（一致性、性能），把话语权抢回来，面试官会顺着你抛的方向问，而不是随便问一个你没准备的点。

### 问题 3：项目中遇到的难点，怎么解决的（最重要，至少准备 3 个）

这是决定面试成败的问题。**别只说一个，下面准备了 5 个，按顺序背，面试官问"还有吗"你要接得上。** 每个都用 STAR（情境-任务-行动-结果），但说的时候不用报"STAR"这个词，自然说就行。推荐优先级：难点 1、2（真实排查过、有测试）＞难点 4（设计深度最高）＞难点 3（真实数据最亮眼）＞难点 5（配合难点 4 一起讲）。

#### 难点 1（首选，最有技术深度）：同步调用超时导致玩家卡死

**一句话结论：** 节点间同步调用超时后，旧代码会让对方处理协程永久卡死，我把它从"无缓冲阻塞发送"改成"带缓冲+非阻塞发送"，并写了能复现问题的测试。

**口语脚本：**

"我们框架里节点之间有个同步调用，等对方处理完再拿结果。原来的写法是：调用方等待用一个**没有缓冲区**的 channel，如果超时了，调用方会先返回。但是被调用的那一方，处理完之后还是会往这个 channel 里塞结果，因为没人接收，这个 channel 会**永远堵住**，那个玩家对应的处理协程就死掉了，后面这个玩家的所有消息都不会再被处理，表现就是这个玩家突然卡住不动了。

这个问题不好排查，因为不会报错、不会崩溃，只是那一个玩家像'冻住'了一样。我是通过写压力测试，模拟一次调用超时之后再发一次正常调用，发现第二次也卡住，才确认是这个原因。

解决办法是把这个 channel 改成**带一个缓冲位**的，这样就算没人接收，超时之后目标那边写进去也不会卡住，会立刻返回。另外我还把 `time.After` 换成了 `time.NewTimer` 加 `Stop`，因为 `time.After` 就算走了别的分支，那个定时器还是会一直占着内存直到真正到期，量大了会增加 GC 压力。

修完之后我专门写了一个回归测试，模拟'调用超时+目标迟到执行完'这个场景，跑 `-race` 确认没问题，这个测试现在也留在代码里，防止以后有人改回去。"

**必带数字/细节（面试官追问会问到）：**
- 无缓冲 channel → 缓冲区大小 1
- `time.After` → `time.NewTimer` + `Stop()`
- 用 `go test -race` 验证
- 写了专门复现"超时后目标是否还能正常工作"的回归测试

#### 难点 2：并发读写导致进程直接崩溃

**一句话结论：** 一个记录节点心跳的 map 被多个 goroutine 并发读写，没加锁，压测时直接 `fatal error: concurrent map writes` 崩进程；补锁后用并发测试验证。

**口语脚本：**

"还有一个是节点健康检查的模块，内部用一个 map 记录每个节点最后一次心跳时间。这个 map 会被两边同时碰：一边是收到心跳就写进去，另一边是有个定时器协程每隔几秒扫一遍找出不健康的节点。原来这个 map 是没加锁的，锁的代码之前被注释掉了。

这种问题最麻烦的地方在于：**它不是每次都出问题**，量小的时候可能一直不报错，但并发一高，Go 运行时会直接检测到'同时读写同一个 map'，直接让整个进程崩溃，报的是 `fatal error: concurrent map writes`，这种是没法用 `recover` 恢复的，直接进程没了。

我是写了一个并发测试，开几十个 goroutine 同时读写这个 map，跑起来立刻就复现了崩溃，日志里能看到具体是哪一行代码出的问题。定位到之后加回一个读写锁：写的地方用互斥锁，读的地方用读锁，因为读的频率比写还高，用读写锁能让多个读之间不互相阻塞。改完之后同样的并发测试跑 `-race` 完全没问题。"

**必带数字/细节：**
- 现场复现的报错：`fatal error: concurrent map writes`
- 用 `sync.RWMutex`（不是普通 `sync.Mutex`），原因是"读多写多，读写锁能让并发读不互相等"
- 修复前后都用同一份并发测试验证

#### 难点 3（用真实数据，Node.js Serverless 项目）：Spin 接口延迟从 300ms 优化到 80ms

**一句话结论：** Spin 接口原来 300 毫秒左右，通过"并行预取 + 两级缓存 + 函数分片 + 副作用异步化"四个动作，压到了 80 毫秒。

**口语脚本（这是你最值钱的一条数据，一定要背熟，讲的时候分四点，逐一停顿）：**

"这个是我另一个项目里的真实优化，是海外 slots 游戏的 Spin 接口，Node.js 写的，部署在 AWS Lambda 上。原来一次 Spin 请求大概 300 毫秒，用户点一下要等三百毫秒才出结果，体感是很明显的卡顿。我们做了四件事，最后压到了 80 毫秒以内。

**第一，把串行请求改成并行。** 原来一次请求里要拿用户信息、拿房间配置、拿 RTP 规则，这几个是分开一步一步查的，改成用 `Promise.all` 一起发出去，等最慢的那个回来就行，不用一个个排队等。

**第二，做了两级缓存降低存储访问延迟。** 局内状态原来是直接读写 DynamoDB，虽然 DynamoDB 本身快，但毕竟是一次网络请求；改成先读 Redis，没有才读 DynamoDB 并回填到 Redis，写的时候也是先写 Redis，再靠一个定时任务批量同步回 DynamoDB，这样热路径完全不用等 DynamoDB 的写延迟。配置这种基本不变的数据，直接放进程内存，用 Redis 里的一个版本号做失效判断，版本没变就一直用内存里的，完全不用跨网络请求。

**第三，把 Spin 单独拆成一组独立的 Lambda 函数，跟其他业务（活动、订单）分开部署。** 这样 Spin 高峰的并发不会跟别的功能抢执行环境，请求进来排队等待的时间也变短了。

**第四，把不影响当次结果的操作挪到异步。** 比如更新排行榜、任务进度、每日活跃这些，Spin 主流程算完结果、扣完钱就直接返回给客户端，这些副作用丢到 SQS 队列里，由另外的消费者异步处理，不卡在返回路径上。

这四个加起来，接口从 300 毫秒降到了 80 毫秒以内。"

**必带数字/细节（面试官追问会问到）：**
- 300ms → **80ms**（不是笼统的"100ms 以内"，这是你真实做到的数字，比同行业常说的"降到 100ms"更有说服力，敢报具体数字本身就是加分项）
- 并行预取用的是 `Promise.all`
- 两级缓存：**Redis 热读 + DynamoDB 兜底**，写是"先写 Redis、定时批量同步回 DynamoDB"（写回/write-behind 思路）
- 配置热数据：**进程内存缓存 + Redis 版本号做失效判断**，不是每次都查 Redis
- Spin 单独分片部署（独立 Lambda 函数组），跟其他业务隔离并发
- 非关键副作用（排行榜/任务/活跃）走 SQS 异步

**面试官大概率追问 1：** "Redis 写完还没同步到 DynamoDB 时，机器挂了怎么办？"  
**答：** "这确实是这套写回缓存的代价，存在一个短暂的数据丢失窗口。缓解手段是同步周期设置得比较短、加失败重试，另外像金币这种真正不能丢的数据，我们是走 PostgreSQL 强一致事务，不走这套 Redis 写回，只有局内进度这种可以'丢一点、追得上'的数据才这样做，这也是一种'按数据重要性分层'的一致性取舍。"

**面试官大概率追问 2：** "为什么不直接把 Spin 也放 Lambda 里加大并发配置就行，为什么要单独分片？"  
**答：** "同一个 Lambda 函数如果什么请求都处理，冷启动、内存、并发限制是共享的，一旦活动或者订单那边流量突然大，会占用原本该给 Spin 用的执行环境配额，Spin 反而变慢。拆开之后 Spin 有自己独立的并发扩缩容配置，互不影响。"

**Go 项目里的类比说法（如果面试官换成问 Go 项目的缓存优化，用这段）：** "Go 那套项目里思路是一样的，也是二级缓存——本地缓存放最热的数据，Redis 做跨节点共享，命中顺序是本地缓存→Redis→数据库，具体数字上不像 Node 项目那组数据这么完整，但降低数据库压力、减少网络往返的思路是一致的。"

#### 难点 4（这是最能体现设计能力的一个，Go 项目，讲的时候可以直接画表结构）：Spin 的幂等 + Outbox 完整设计

**一句话结论：** 消息重试可能导致同一个请求被处理两次，通过"唯一键幂等 + 同事务 Outbox + 带租约的后台中继 + 局内状态异步写队列"这一整套，保证钱不会错、事件不会丢、也不会全表扫描拖垮数据库。

**口语脚本（分五步说，这是本场面试含金量最高的一段，建议逐字背下来数字和关键词）：**

"游戏里的 Spin 会涉及扣钱、发奖励，客户端弱网重试或者消息重投都可能让同一个请求被处理两次，这是绝对不能接受的。我把这块拆成五步：

**第一步，请求先回放判断。** 每次 Spin 请求带一个 `requestId`，进来先按 `(用户ID, 操作类型, requestId)` 去查一张操作记录表，如果已经有一条状态是 COMPLETED 的记录，说明这个请求之前已经处理完了，直接把当时存的响应原样返回给客户端，**不会重新跑一次抽奖逻辑**，也不会重新扣钱。

**第二步，真正处理的时候，所有操作在同一个数据库事务里做完。** 具体是四件事：先插入这条操作记录（这一步本身也是幂等的第二道保险，因为这张表上有唯一索引，并发重复请求只有一个能插入成功，插入失败说明是重复请求，会转去走回放逻辑）；然后是**条件更新扣钱**，写法类似 `UPDATE ... SET money = money - 下注额 WHERE money >= 下注额`，不是先查余额再算减法，避免竞态；然后写一条 append-only 的账本记录，只增不改，方便对账；最后**在同一个事务里**插入一条状态是 PENDING 的 Outbox 事件记录。这四件事要么全成功要么全失败，不会出现钱扣了但事件没写、或者反过来的情况。

**第三步，事务提交之后，才有一个独立的后台任务（我们叫它 Relay）去把 PENDING 的事件真正发到消息队列。** 这里有个细节我觉得能体现设计深度：Relay 去捞 PENDING 记录时用的是 `FOR UPDATE SKIP LOCKED`，就是如果这条记录已经被别的 Relay 实例锁住在处理，就跳过去处理下一条，而不是排队等，这样多个游戏节点上的 Relay 可以**并发抢事件**而不是互相阻塞。抢到之后会给这批事件标记一个'谁在处理、锁到什么时候'的租约，处理成功就标记 PUBLISHED，如果发送失败或者进程挂了，租约过期后别的实例可以重新接手，重试次数是不设上限的，因为只有真正发送成功到消息队列才算完成，退避时间是指数增长、封顶在 5 分钟，不会因为一次故障就把数据库打爆。

**第四步，避免全表扫描。** 这张 Outbox 表专门建了一个**部分索引（partial index）**，只对状态是 PENDING 的行建索引，Relay 每次轮询只会命中这个很小的索引范围，不会随着历史发送记录越堆越多而扫描越来越慢，这个是我们上线前专门加的一个优化点。

**第五步，发到消息队列这边，用的是 NATS 的 JetStream，发送的时候带了一个消息去重用的 ID（`Nats-Msg-Id`），JetStream 在配置的时间窗口内会对同一个 ID 去重，这样即使 Relay 因为超时重试导致同一个事件发了两次，JetStream 那一层也能挡掉一部分重复。但这个去重窗口是有时间限制的，不能保证业务上绝对的精确一次，所以消费方（比如活动系统）自己也有一个基于事件 ID 的幂等记录，双重保险。"

**必带数字/细节（面试官追问会精确到这些点，一定要记住关键词）：**
- 幂等唯一键：`(用户ID, 操作类型, requestId)` 唯一索引
- 扣钱是**条件更新**（`WHERE money >= 下注额`），不是"先查再减"
- 账本表是 **append-only**，只插入不修改
- Outbox 表状态机：`PENDING → PUBLISHED`，字段包括 `locked_by`（租约持有者）、`locked_until`（租约到期）、`next_attempt_at`（下次重试时间）、`retry_count`
- Relay 抢占用 `FOR UPDATE SKIP LOCKED`，多实例**竞争而不是阻塞**
- 避免全表扫描：**部分索引 `WHERE status = 'PENDING'`**
- 消息队列是 **NATS JetStream**，用 `Nats-Msg-Id` 头做时间窗口内去重
- 消费方还有独立的幂等记录，因为 JetStream 去重窗口不能证明"业务层精确一次"

**面试官大概率追问：** "为什么不是先 Commit 事务，再发 NATS？"  
**答：** "如果先 Commit 再发消息，中间万一进程崩了或者网络抖动，消息就永远发不出去了，而且这时候钱已经真实扣了，没法回滚。把'要发的消息'当成数据，跟业务操作在同一个事务里落地，可以保证'钱扣成功'和'这条事件一定会被产生'是同一个原子操作，之后事件有没有发出去可以靠独立的 Relay 不断重试来保证，这个重试是安全的，因为 Relay 不会重新执行业务逻辑，只是重新发消息。"

#### 难点 5（配套难点 4，讲局内状态怎么异步落盘）：Spin 的局内进度怎么做到"不卡请求路径"又"不丢数据"

**一句话结论：** 局内状态（比如这局玩到哪一步）不会每次 Spin 都同步写数据库，而是提交给一个按玩家分片的写队列，攒够一批或者到时间就批量落盘。

**口语脚本：**

"Spin 主流程算完钱之后，还要保存这局的房间状态，但这个不应该卡住给客户端的响应。做法是搞了一个**异步写队列组件**：每张表配置几个 worker，每个 worker 有自己的 channel。提交任务的时候按 `玩家ID 对 worker 数量取模` 选一个 worker，这样能保证**同一个玩家的数据永远进同一个 worker**，不会因为并行写乱了顺序。worker 内部用一个 map 做去重合并——同一个玩家同一个房间如果连续产生好几次要保存的任务，只保留最新的那一份，减少真正写库的次数。什么时候真正落盘：一是攒够设定的条数就触发一次批量写，二是有个定时器，到了固定间隔没攒够也会强制刷一次，保证数据不会等太久。停服的时候，会把批量写入的阈值临时调小、尽快把队列里剩下的全部刷完，并且失败会用指数退避重试，保证进程退出前数据基本落地。"

**必带细节：** 按 `PlayerID % worker数量` 分片保证同玩家顺序、内存 map 按 key 去重合并、"攒够条数或到时间"双触发落盘、停服时收紧批量阈值加速排空。

### 问题 4：Spin 高并发、低延迟、数据一致性怎么解决的（重点，技术官会深挖）

**一句话结论：** 高并发靠"按玩家分片的 Actor"天然并行不用锁；低延迟靠"热数据走内存+异步落盘"；一致性靠"分层处理"——钱强一致，进度最终一致。

**口语脚本（分三段，这是本场面试的技术高光时刻，建议重点背）：**

**1. 高并发怎么做：**

"Spin 是最高频的接口，人一多，如果所有人抢同一把锁，肯定顶不住。我们的做法是**按玩家分片**：每个玩家对应一个独立的 Actor，这个玩家所有的 Spin 请求都会进到同一个 Actor 的消息队列里**排队串行处理**，不同玩家之间是完全独立、并行跑的。这样天然就避免了'一个全局锁卡住所有人'的问题，同一个玩家自己也不会因为连续点击而把数据搞乱，因为消息是排队处理的。"

**2. 低延迟怎么做：**

"能同步做的东西越少，接口越快。我们把不着急的操作都挪到了异步：比如配置这种不常变的数据，直接放本地缓存，不用每次都查库；玩家的房间进度这种数据，先改内存，然后异步批量写到 Redis 或者数据库，不卡在请求路径上；还有消息通知这块，也是先在内存里标记一下要发，实际发送交给后台单独的协程去做，主流程不用等它。"

**3. 数据一致性怎么做（这里最容易被深挖，一定要讲清楚"分层"这个概念）：**

"数据不是所有的都要求一样级别的一致性，我们是**分层处理**的：

跟钱有关的，比如余额，这个必须是强一致的，不能有任何差错。这块是走数据库事务，加上前面说的 requestId 幂等判断，保证同一个请求不管重试几次，结果都一样，钱不会多扣也不会少扣。

跟游戏进度相关的，比如玩到第几关、剩多少道具，这种可以接受**短暂的不一致**，走的是先改内存、后台异步落盘，就算落盘慢一点，也不会影响玩家体验，最终数据会追上。

这样分开处理的好处是：不会为了保护一小部分核心数据（钱），把所有数据都用最重的事务锁起来，导致整体性能下降。"

**面试官大概率追问 1：** "Actor 之间怎么协调，比如查这个玩家钱够不够？"  
**答：** "如果 Spin 这个 Actor 需要玩家的余额信息，会同步调用管理玩家资产的那个 Actor 拿数据，真正扣款的时候是在数据库层面做条件更新，比如'余额大于等于要扣的钱才更新'，不是在内存里锁一个变量去减。"

**面试官大概率追问 2：** "如果这个玩家的 Actor 处理特别慢，或者卡住了怎么办？"  
**答：** "这个就是我前面难点 1 讲的问题——同步调用要有超时保护，而且超时之后不能让被调用方卡死，我们专门做过这个修复。另外从设计上，Actor 里不应该做太重的阻塞操作，重的 IO 都应该是异步化的。"

### 问题 5：怎么保证服务的稳定性（高可用）

**一句话结论：** 高可用不是靠"堆机器"，是接入层能路由、计算层能隔离故障、数据层能重试、加上完善的监控报警。分四层讲。

**口语脚本：**

"稳定性这块我分四个层面来说：

**第一，接入层。** 客户端连接会做粘性路由，就是同一个玩家的连接固定分配到某个节点，方便管理状态；节点如果不健康，会被健康检查发现，不会再把新连接分给它。另外像 WebSocket 握手这种入口，我们给它加了超时限制，防止有恶意连接故意占着不放，把连接资源耗尽。

**第二，计算层，也就是故障隔离。** 前面讲的 Actor 模型本身就是一种隔离：一个玩家的 Actor 出问题，理论上不会直接影响其他玩家，但如果没做好超时保护，是有可能因为一次调用把一个 Actor 卡死的，这个我们已经修复了。

**第三，数据层。** 关键数据比如余额的操作要保证幂等，就算重试也不会出错；用消息队列加 Outbox 保证消息不丢，中间件比如数据库、Redis 挂了短时间，靠重试机制能扛过去。

**第四，可观测性。** 用 Prometheus、Grafana、CloudWatch 做监控，关键指标比如 CPU、内存、goroutine 数量、GC 情况都在看，出问题会报警到邮箱和飞书；我们还做了一个功能，就是一旦触发严重告警，会自动把当时的 CPU、内存快照抓下来存到本地，因为很多问题等你人工登录上去查的时候，现场已经过去了，有自动抓取就能保留第一手证据去分析根因。"

**必带数字：** CloudFront + 日志系统配合，做到 **99.98%** 可用性；峰值 **10000 QPS**。

## 二、一面可能追问清单（偏基础/广度）

一面通常是筛选，问题不会特别深，但会看你**基础扎不扎实、说话是否清楚**。每题给"最优简答"，不用像上面那么长，控制在 20-30 秒。

| 问题 | 最优简答要点 |
|---|---|
| Goroutine 和线程的区别？ | goroutine 是用户态调度的轻量协程，创建和切换开销比操作系统线程小很多，一个进程能开几十万个；由 Go 运行时的调度器（GMP 模型）负责映射到少量操作系统线程上。 |
| Channel 缓冲和非缓冲的区别？ | 无缓冲 channel 发送方和接收方要同时就位才能完成通信，相当于同步交接；带缓冲的 channel 只要缓冲区没满，发送方可以先放进去就返回，不用等接收方。我们那个超时死锁的 bug，本质就是无缓冲 channel 在没人接收时会一直卡住。 |
| 简单说一下 GMP 模型 | G 是 goroutine，M 是操作系统线程，P 是调度用的上下文（可以理解成"许可证"，决定同时能有多少 M 在真正跑 Go 代码）。P 的数量一般等于 CPU 核数，G 不是直接绑定 M，而是排在 P 的队列里，由调度器分配给空闲的 M 执行，这样切换 goroutine 不需要陷入内核态，很快。 |
| 为什么用 Actor 模型而不是直接开锁保护共享数据？ | 锁的问题是粒度不好控制，锁太粗影响并发，锁太细容易死锁、也容易漏加。Actor 模型把数据和处理它的逻辑绑在一起，外部只能通过发消息访问，同一个 Actor 内部是单线程处理，天然不会有数据竞争，心智负担更小。 |
| NATS 和 Kafka/SQS/gRPC 的区别？ | 简答见下表；**详细版见本节后面的"专题：消息中间件与 RPC 怎么选"，二面大概率会顺着这个问题一直往下挖，务必看那一节。** |
| 为什么要用 Outbox 模式，直接发消息不行吗？ | 直接发消息会有"写库成功但发消息失败"或者反过来的问题，两个操作不在一个事务里，没法保证一致。Outbox 是把'要发的消息'也当成数据，跟业务数据在**同一个事务**里写，事务成功消息才算真正产生，然后由后台任务保证把这条消息发出去，发送本身可以重试，不影响业务事务。 |
| 为什么迁移到 Serverless？ | 主要是应对游戏高峰期这种突发流量，自己维护固定数量的服务器要么高峰扛不住，要么平时资源浪费。Serverless 按请求量自动扩缩容，配合 DynamoDB 这种能自动扩展的数据库，可以更好地应对流量波动，也省了不少运维精力。 |
| 项目里用 Redis 主要做什么？ | 分布式缓存，减少重复查库；也会存一些像在线状态、心跳时间这种需要跨节点共享、时效性要求不高的数据。 |
| 你怎么用 AI 工具（Cursor/Codex）辅助开发？ | 主要用来做代码排查和重构，比如让它帮忙定位并发问题、生成单元测试。但**关键改动我都会自己过一遍逻辑，跑测试和 `-race` 验证**，不会直接把 AI 生成的代码不看就合进去，尤其是涉及并发和资金的逻辑。 |
| 你的职业规划 / 为什么看这个机会 | 根据实际情况自己准备，建议突出"想在分布式/高并发方向继续深入"这类和岗位强相关的话。 |

## 三、二面可能追问清单（偏深度/架构/设计）

二面通常是资深工程师或架构师面，会顺着你简历和一面聊到的点**往细了挖**，甚至让你画图讲设计。

| 问题 | 最优简答要点（讲思路，别只背结论） |
|---|---|
| 详细画一下 Outbox 的完整流程，数据库设计是怎样的，会不会全表扫描？ | **完整版直接看上面"难点 4"**，那里有表结构、`SKIP LOCKED`、部分索引、JetStream 去重的全部细节，别只说教科书版本，说出具体字段名和索引设计，可信度差很多。 |
| Outbox 的后台任务如果部署了多个实例，会不会重复发送同一条消息？ | 会有这个风险，处理办法是**加租约（lease）机制**：一个实例去捞消息的时候，先给这批消息标记一个"谁在处理、到什么时候"的租约，其他实例发现租约没过期就跳过；如果这个实例处理到一半挂了，租约过期后别的实例可以重新接手。就算真的重复发了，消费方的幂等处理也能兜底。（这里的抢占具体是用 `FOR UPDATE SKIP LOCKED`，抢不到的直接跳过而不是排队等锁，吞吐更好。） |
| Spin 算完之后，局内状态是怎么落库的？会不会拖慢响应？ | **看上面"难点 5"**：不会同步写库，是提交到一个按玩家 ID 分片的异步写队列，攒够批量或者到时间间隔就批量落盘，同一个玩家的多次写会在内存里合并去重，只保留最新的一份，减少真正的 IO 次数。 |
| requestId 幂等具体怎么实现的，数据库层面怎么设计？ | 在结算表上对 `(用户ID, 操作类型, requestId)` 建唯一索引。处理请求时直接尝试插入这条唯一记录，如果插入冲突（说明这个请求已经处理过），就不再重新执行业务逻辑，直接把之前存的结果查出来原样返回给客户端；如果插入成功，才继续走扣款、发奖励的正式逻辑。这样保证同一个 requestId 无论重试多少次，业务只会真正执行一次。 |
| 为什么余额扣款不在内存里加锁，而是用数据库条件更新？ | 内存锁只在单个进程、单个节点内有效，一旦是多节点或者哪天要跨进程访问，内存锁就保护不住了。而数据库的条件更新（比如 `UPDATE ... SET balance = balance - N WHERE balance >= N`）是数据库层面保证的原子操作，不管多少个节点同时来更新，数据库能保证同一时刻只有一个更新会成功，天生具备跨节点的一致性保护，不依赖进程内的锁。 |
| Actor 模型下，如果某个 Actor 处理的消息堆积了怎么办（背压）？ | 可以从几方面：一是给每个 Actor 的消息队列设置容量上限，超过了就拒绝新消息或者返回繁忙，而不是无限堆积占内存；二是从源头限流，比如同一个玩家短时间内的请求频率做限制；三是监控每个 Actor 的队列长度，作为一个可观测指标，堆积到一定程度就报警，方便定位是哪类 Actor、哪个场景出现的瓶颈。 |
| 数据竞争（data race）和普通的并发 bug 有什么区别？为什么要专门用 `-race` 检测？ | 普通并发 bug 比如死锁、逻辑错误，很多时候能通过日志、复现步骤定位。但数据竞争在 Go 的内存模型里是"未定义行为"——没有同步保护的跨协程读写，读的一方**不保证**能看到写的一方的最新结果，这不是"运气不好偶尔读到旧值"，理论上可以一直读到旧值，而且不同硬件、不同编译器优化下表现可能都不一样，很难靠肉眼看代码发现，也很难稳定复现。`-race` 是 Go 工具链内置的检测器，能在运行时监控内存访问，一旦发现没有同步保护的并发读写会立刻报告出来，包括具体是哪个协程、哪一行代码，这是目前定位这类问题最可靠的手段，比人工 review 靠谱得多。 |
| 从自建 Golang 分布式服务迁移到 Serverless，过程中踩过什么坑？ | 可以从这几个角度准备：冷启动延迟（Lambda 长时间没调用会有启动耗时，可能需要预热策略）；DynamoDB 的数据建模跟关系型数据库思路不一样，要按访问模式设计分区键，不能照搬原来关系型的表结构，dynamodb比较扩容比较慢，需要手动提前扩容，或者出现报错时，手动扩容和请求熔断（幂次等待）；Serverless 下调试（需要去看couldWatch日志）和本地开发不如自建服务方便，需要额外的本地模拟工具。**如果确实没有深入踩过这些坑，诚实说"这块我们主要是按 AWS 官方最佳实践去做的分区键设计和预留并发配置，没有遇到特别严重的问题"，不要硬编造细节。** |
| 分库分表的策略是怎么定的，为什么按 schema 分而不是按表名后缀分？ | 按用户分组用不同 schema，管理上更清晰，权限、备份、迁移都可以按 schema 为单位操作，运维上比按表名加后缀（比如 order_001）更直观；缺点是如果某个 schema 的数据量远超其他的，会有热点问题，需要提前预估好分组规则，或者预留后续再拆分的能力。 |
| 限流、熔断具体是怎么做的？特别是 DynamoDB 这种自动扩容但不是按需计费的情况？ | 简答见下方**"专题：限流熔断——以 DynamoDB 预留容量突发流量为例"**，这是加分题，DynamoDB 预留容量模式下自动扩容有延迟，是个很好的展示点。 |
| gRPC 用得多吗，和你们用的 NATS RPC 有什么区别？如果这个岗位大量用 gRPC 呢？ | 简答见下方**"专题：gRPC vs NATS"**，如果目标岗位明确要求 gRPC，这节要重点看。 |
| 让你重新设计这套系统，你会改哪里？ | 展示反思能力，可以说：会考虑把关键路径的同步调用尽量都改成有超时保护和熔断的模式，不依赖开发者每次都记得手动加；监控这块想更早接入自动化的异常快照采集，而不是等出了大问题才补；Actor 之间的调用链路想加更完善的链路追踪，方便一次请求跨多个 Actor 时定位是哪一跳慢。 |

### 专题：消息中间件与 RPC 怎么选（NATS / Kafka / SQS / gRPC）

这是二面高频的架构选型题，面试官想看的不是你背没背过定义，而是你能不能讲清楚**每种工具在你项目里具体解决了什么问题**。

**先给一张对比表（心里有这张表，回答就不会乱）：**

| 维度 | NATS Core | NATS JetStream | Kafka | SQS | gRPC |
|---|---|---|---|---|---|
| 模型 | 消息代理，发布订阅/请求响应 | NATS 加持久化层 | 分布式日志，分区+消费组 | 云托管队列 | **点对点**远程调用，无中间代理 |
| 投递保证 | 最多一次，不持久化，进程重启就丢 | 至少一次，可持久化到磁盘 | 至少一次/精确一次（配合事务） | 至少一次 | 无内置保证，靠业务自己做重试/幂等 |
| 延迟 | 微秒到毫秒级，非常快 | 比 Core NATS 高一点（要落盘、要 Ack） | 中等，批量吞吐大但单条延迟不如 NATS | 较高（HTTP 轮询式，有几十到上百毫秒延迟） | 低，长连接 + HTTP/2 多路复用 |
| 顺序保证 | 不保证 | 单个 subject 内保证顺序 | 分区内保证顺序 | 标准队列不保证，FIFO 队列保证但吞吐更低 | 不适用（是调用不是队列） |
| 运维复杂度 | 很低，单二进制 | 低，比 Kafka 简单很多 | 高，要管 ZooKeeper/Controller、分区再均衡 | 无需自己运维（云托管） | 低，但需要处理服务发现和负载均衡 |
| 典型用途 | 低延迟 RPC、心跳、状态广播 | 需要重放/持久化的业务事件 | 海量日志/流式计算 | 云上简单解耦、削峰 | 内部服务间强类型调用 |

**口语脚本（怎么把这张表讲成一段有说服力的话）：**

"这几个工具我是按'要不要持久化''要不要点对点'这两个维度来选的：

**NATS Core** 我们用来做节点之间的同步调用，比如一个 Actor 要问另一个 Actor 要数据，用的是 Request/Reply 模式，因为**足够轻量、延迟低**，但它是'最多一次'投递，进程重启这条消息就没了，所以只适合这种'问完立刻用、用完就扔'的场景，不能用来传不能丢的业务事件。

**NATS JetStream** 我们用在 Outbox 往外发事件的场景，因为这个事件不能丢，需要落盘、需要重试、需要给消费方一个'去重'的窗口，JetStream 刚好补上了 Core NATS 不持久化的短板，而且运维成本比 Kafka 低很多，适合我们这种不需要 Kafka 那种海量分区吞吐的场景。

**Kafka 和 SQS** 我没有在这个项目里直接用，但理解它们的场景：Kafka 更适合日志采集、流式计算这种**吞吐量极大、需要多消费组重复消费同一批数据**的场景，比如一份订单流水既要给风控用又要给报表用；SQS 是云托管的，不用自己运维，比较适合**简单的任务队列削峰**，比如我另一个 Serverless 项目里，Spin 完之后的排行榜更新、任务进度这些'次要动作'就是丢到 SQS 里异步处理，换成 Kafka 反而运维成本更高，没必要。

**gRPC 和 NATS 的核心区别**是有没有中间代理：gRPC 是调用方直接连到服务方，效率高但需要自己解决'去哪儿找到对方、对方挂了怎么办'（也就是服务发现和负载均衡）；NATS 是通过中间的消息代理转发，调用方完全不用知道谁在处理，服务方扩容缩容对调用方是透明的，代价是多了一次中转的延迟。我们框架选 NATS 的原因，就是内部有大量动态创建/销毁的 Actor，如果用 gRPC 点对点，服务发现这块自己维护的成本会很高。"

**面试官大概率追问：** "如果要求你们上 Kafka，你会遇到什么问题？"  
**答：** "主要是运维复杂度上升——Kafka 需要维护分区数量、副本、消费组的再均衡，如果流量没有大到需要 Kafka 那种吞吐量级，引入它反而是负担；技术上要重新设计 Key 的分区策略，保证同一个用户的事件还能保序，这个和我们现在 NATS JetStream 单 subject 保序的思路是类似的，可以迁移过去，不是从零设计。"

### 专题：gRPC vs NATS，详细讲法和注意事项（目标岗位可能大量用 gRPC，重点看）

如果 JD 里明确写了 gRPC，说明这块面试官会问得比较细，下面按"是什么、怎么用、有什么坑"分层准备。

**1. 核心区别，一句话说清楚：**

"gRPC 是**点对点**的强类型 RPC，基于 HTTP/2；NATS 是**通过中间代理转发**的消息系统。gRPC 像是打电话，你要直接拨对方的号码；NATS 像是发到一个广播频道，谁在监听那个频道就能收到，你不需要知道对方是谁、在哪。"

**2. gRPC 具体怎么用（如果被要求现场设计或者讲实现细节）：**

- **接口定义**：用 Protobuf 定义 service 和消息结构，`protoc` 生成客户端/服务端代码，天然强类型、跨语言。
- **四种调用方式**：一元调用（一请求一响应，最常见）、服务端流（一个请求、多个响应，比如订阅一个不断更新的状态）、客户端流（多个请求、一个响应，比如批量上传）、双向流（两边都能持续发，比如实时聊天/游戏同步）。**长连接推送场景可以考虑服务端流或双向流替代轮询。**
- **超时和取消**：gRPC 有内置的 `context`/`deadline` 机制，调用时设置超时，服务端能感知到调用方已经取消，可以提前终止处理，这个和我们框架里 `CallWait` 手动维护超时的思路是一样的，只是 gRPC 把这个机制做进了协议层。
- **错误处理**：用标准的 `status`/`code`（比如 `NOT_FOUND`、`DEADLINE_EXCEEDED`、`UNAVAILABLE`），不要用普通字符串错误，方便客户端按错误码分类处理、决定要不要重试。
- **拦截器（interceptor）**：可以在这里统一做鉴权、日志、链路追踪、限流，类似中间件，不用在每个接口里重复写。

**3. 生产环境容易踩的坑（这几个点能体现你不是只会 hello world）：**

- **负载均衡问题**：gRPC 基于 HTTP/2，一个连接上会复用多个流（stream），如果只在 TCP/连接层做负载均衡（比如简单的 L4 负载均衡器），流量会**长期压在建立连接时选中的那一个后端**，不会像 HTTP/1.1 那样每个请求都重新分配。生产上一般要用支持 gRPC 的 L7 负载均衡（比如 Envoy、或者客户端负载均衡库），否则会出现某几台机器过载、其他机器很闲的情况。
- **心跳与连接保活**：长连接场景要配置 `keepalive`，避免中间的网络设备（比如某些云厂商的负载均衡）因为连接空闲太久把它悄悄断掉。
- **服务发现**：gRPC 本身不管"去哪儿找服务"，需要搭配注册中心（比如 etcd、Consul）或者服务网格，这个和我们项目里用 etcd 做节点注册的思路是通的，可以直接迁移这部分经验。
- **Proto 版本兼容**：字段只能新增不能随便删/改类型，不然新旧版本的客户端和服务端互相调用会出问题，要按 Protobuf 的兼容性规则升级接口。

**4. 如果面试官问"你会怎么把 gRPC 加到 Cherry 这套框架里"（现场设计题）：**

"我会把它放在**跨语言/跨系统边界**的地方，比如游戏服务要对接一个用 Java/Python 写的支付服务、或者风控服务，这种场景强类型接口 + 跨语言生成代码的优势很明显，用 gRPC 比较合适。但**框架内部 Actor 之间**我还是会继续用 NATS，因为 Actor 数量动态变化、需要解耦寻址，NATS 的代理转发模式更省心，没必要为内部通信引入服务发现的复杂度。简单说就是——**内部用 NATS，对外/跨语言边界用 gRPC**，两者不冲突，按场景混用。"

**如果你确实经验不深，诚实但体面的说法：** "我们框架内部通信主要用 NATS，gRPC 用得不多，但我理解它的协议模型、四种流模式和落地时要注意的负载均衡、服务发现这些问题；如果贵司这边大量用 gRPC，我上手它的语法和工具链会比较快，需要补的主要是具体业务场景下的实战经验。"

### 专题：限流熔断——以 DynamoDB 预留容量突发流量为例

这是一个**很好的加分题**，因为大多数候选人只会说"令牌桶、熔断器"这种教科书答案，你可以用一个具体场景讲清楚，显得经验更真实。

**场景铺垫（先讲清楚为什么这是个真问题）：**

"DynamoDB 有两种计费模式：按需（On-Demand）和预留容量（Provisioned，可以配自动扩缩容）。预留容量模式下，**自动扩容不是瞬时的**，AWS 是根据过去一段时间的使用率逐步调整容量的，一般有几分钟的滞后。如果游戏突然搞了个活动，瞬间涌入的流量远超过当前预留的读写容量，会先打出 `ProvisionedThroughputExceededException`（**限流报错**），而不是立刻自动扩容接住这个流量。这时候如果没有保护机制，大量请求都在疯狂重试打 DynamoDB，会让节流情况更严重，甚至把重试请求本身变成一次'自己打自己'的雪崩。"

**具体怎么做，分三层：**

**第一层，入口限流，别让流量原样怼到 DynamoDB。** 在应用层/接口入口按照当前预留容量的水位设置一个令牌桶，速率设置得比预留的 RCU/WCU 略低一点，主动削峰，而不是全部放行让 DynamoDB 自己去扛。

**第二层，熔断，别在已经出问题的时候继续加重伤害。** 监控对 DynamoDB 调用的错误率，一旦'限流错误'的比例超过一个阈值（比如 50%），就在接下来一小段时间内直接让新请求快速失败或者走降级逻辑（比如回退到读缓存里的旧数据、或者返回'请稍候'），不再继续打 DynamoDB，避免把有限的容量继续浪费在注定失败的请求上；过一段冷却时间后，放一小部分请求进去'试探'，如果成功率恢复了再逐步放量，这就是熔断器的**关闭 → 打开 → 半开**三态。

**第三层，从架构上削峰，不完全依赖运行时保护。** 比如把非实时不可的写操作先进队列（类似我们 Go 项目里那个按玩家分片的写队列思路），批量攒起来再写 DynamoDB，减少单位时间内真正打到 DynamoDB 的请求数；另外可以给关键路径（比如 Spin 扣钱）预留单独的一部分容量，跟非关键路径（比如日志、统计）分开，即使非关键路径被限流，也不影响核心流程。

**必带关键词：** `ProvisionedThroughputExceededException`、预留容量自动扩容有滞后（不是按需实时）、令牌桶主动削峰、熔断三态（关闭/打开/半开）、错误率阈值、批量写削峰、关键路径与非关键路径容量隔离。

**面试官追问：** "为什么不干脆都用按需计费模式，不就没有这个问题了？"  
**答：** "按需模式确实能自动应对突发流量，不会有这种滞后问题，但成本比预留模式贵不少，而且账单会随流量波动，团队通常是核心表用预留容量做成本控制、配合自动扩缩容，非核心/流量不稳定的表用按需模式，这也是一种'按访问模式选型'的取舍，不是非黑即白。"

## 五、表达技巧（针对"表达能力一般"专门给的建议）

1. **先说结论，再说过程。** 面试官时间有限，你先说"结果是从 300ms 降到 80ms"，他感兴趣自然会追问怎么做的；先讲一堆过程再说结果，容易讲到一半忘了重点，或者面试官没耐心听完。
2. **用"第一、第二、第三"分点，哪怕只是口头说。** 这是最简单能让"表达一般"变成"逻辑清楚"的技巧，不需要文采，只需要分点。
3. **数字比形容词有用。** "很快"不如"300 毫秒降到 80 毫秒"；"经常出问题"不如"压测的时候必现"。背数字比背句子容易，效果却更好。
4. **不会的问题，别硬编，说思路。** 比如熔断、gRPC 这种你可能经验不深的点，按上面给的话术说"了解原理、这块经验不算深"，然后**转到你熟悉的相邻话题**（比如从"熔断"转到"我们做的超时保护"），面试官通常会顺着走，比你硬编一个假细节被追问出破绽安全得多。
5. **说完一段，允许自己停顿 1-2 秒。** 不用怕冷场，磕巴地说完整比流畅地说错强。

## 六、忌讳提醒（容易被戳穿的点）

- **最重要的一条**：分清楚"哪句话是哪个项目的"（见前面〇.1 的边界表）。NATS/WebSocket 只属于 Go 项目，Lambda/DynamoDB/Firehose/Athena/CloudFront/300ms→80ms 只属于 Node.js 项目，Outbox 表结构细节只属于 Go 项目（Node 项目讲"SQS+写回"）。混着讲是最容易被追问戳穿的地方，比任何单个技术细节答错都致命。
- 简历里 Cocos Creator/Unity3D、SQS 具体运维细节、API 网关熔断落地这几项，如果实际接触不深，**不要主动展开讲细节**，被问到时用"了解原理，做得不算深"的话术，别硬装精通，二面的人大概率比你懂，一问就露馅。gRPC 和限流熔断已经在上面两个专题里给了足够细节，可以讲得比"了解原理"更深一点。
- 不要把"我们团队做的"说成"我一个人做的"，可以说"我主导/负责其中 XX 部分"，显得更真实也更谦逊，面试官反而更信。
- 数字要能自圆其说：如果说 10000 QPS，被追问"单机还是集群、用什么压测工具测的"，要能接得住，接不住就适当说"这是团队整体压测的峰值数据，具体压测工具我了解得不算特别细"。Athena/Grafana 如果不是你亲手搭的，用"平台/运维侧能力，我主要是使用者"这种说法。
- 难点 1、2（超时死锁、并发 map 崩溃）、难点 4、5（Outbox 全套设计）你是**真的排查过/设计过、有代码有测试验证**的，这是你最大的加分项，讲的时候要有具体细节（报错文字、字段名、索引类型），细节越具体，可信度越高，这几个可以讲得比其他项更细、更有把握。

## 八、岗位 JD 对齐：最看重什么，项目里对应什么

> 目标岗位：电商客服 SaaS 后端。JD 真正看重的不是「会不会写 CRUD」，而是 **实时会话链路 + 消息可靠投递 + 数据一致性 + 线上排查**。下面按「岗位最看重什么 → 你项目里对应什么」对齐，面试前扫这一节即可。

包装口径建议用这句话开场：

> 「我做的是 Go 分布式实时业务系统：长连接接入、按用户串行的状态处理、跨节点消息、以及 Outbox 可靠异步。业务壳是游戏会话，但和客服 SaaS 的在线会话、消息推送、可靠投递、状态一致性是同构的。」

### 8.1 该岗位最看重的技术场景（按重要程度）

| 优先级 | 岗位真实关心的场景 | JD 对应点 | 为什么重要 |
|---|---|---|---|
| **P0** | 消息可靠投递：不丢、可重试、可幂等 | 职责5：Kafka/Redis/Outbox/ACK/重试/幂等 | 客服消息、工单、订单状态同步一旦丢/重，直接影响生意 |
| **P0** | 长连接实时通信：在线、路由、推送 | 职责4/7：WebSocket、消息推送、在线状态、gRPC | 客服 SaaS 的核心体验就是「人在不在线、消息能不能即时到」 |
| **P0** | 多存储一致性：库 + 缓存 + 异步 | 职责6、任职3/5：MySQL/Mongo/Redis、缓存一致性 | 订单/会话状态分散在多处，一致性设计是日常主战场 |
| **P1** | Go 服务工程化：接口、缓存、定时/异步任务 | 职责3、任职2 | 日常交付底座 |
| **P1** | 线上定位与性能优化 | 职责10、任职7 | 客服高峰期出问题要能快速止血 |
| **P2** | AI 工具辅助研发，且能审 AI 产出 | 职责11、任职9/10 | JD 写得很重，但偏工作方式，不是业务核心 |
| **P2** | 业务域对接（订单/工单/平台开放接口） | 职责1/8/9 | 业务壳不同，看迁移表达能力 |

### 8.2 项目里「同构」的场景与方案（可直接讲）

#### 1. P0：消息可靠投递（岗位 Kafka/Outbox/ACK/重试/幂等）

**岗位场景：** 写库成功后，还要保证下游一定收到事件（客服消息落库 → 推送/工单/统计）。

**你项目同构方案：** Spin 结算同事务写 Outbox → Relay 投递 JetStream → 消费方按 eventId 幂等。

| 岗位说法 | 你项目对应 | 证据位置 |
|---|---|---|
| Outbox 本地消息表 | `domain_outbox`，事务内写 PENDING | `internal/asset/settlement.go` |
| 后台可靠投递 | Relay：`FOR UPDATE SKIP LOCKED` + 租约 + 指数退避 | `internal/component/outbox/relay.go`、`repository.go` |
| ACK / 至少一次 | JetStream 持久化 + MsgId 窗口去重 | `internal/component/outbox/publisher.go` |
| 幂等 | `(user_id, operation_type, request_id)` 唯一键 + 结果回放 | `settlement.go` + `level_room.go` spin 入口 |
| 避免全表扫 | 部分索引 `WHERE status='PENDING'` | `docs/sql/20260804_outbox_relay.sql` |

**一句话翻译：** 岗位说 Kafka，你说「我们用 NATS JetStream 做同样的至少一次投递；Outbox/ACK/重试/幂等这套模式是完全同构的」。细节直接用上面「难点 4」。

#### 2. P0：长连接 + 在线状态 + 消息路由推送（岗位 WebSocket/gRPC）

**岗位场景：** 坐席在线、会话路由、实时消息推送。

**你项目同构方案：** Gate WebSocket 接入 → Session 粘滞路由 → 跨节点推送。

| 岗位说法 | 你项目对应 | 证据位置 |
|---|---|---|
| WebSocket 长连接 | Gate 接入、握手超时、连接生命周期 | `cherry/net/connector/ws_connector.go`、`nodes/gate/` |
| 在线状态管理 | Session / 节点健康检查 / 粘性路由 | `nodes/gate/actor_agent.go`、`route.go`、`node_health_checker.go` |
| 消息路由与推送 | Gate 按 ServerID/Session 路由到 Game Actor，再回推客户端 | `nodes/gate/route.go`、Pomelo push 链路 |
| 跨服务 RPC | 节点间 NATS Request/Reply（对应岗位 gRPC 角色） | Cherry NATS cluster / CallWait |

**一句话翻译：** 岗位要 gRPC 点对点 RPC；你有 NATS RPC。讲清楚「内部动态 Actor 用消息代理更合适；对外/跨语言边界用 gRPC」即可，不要假装本项目大量用了 gRPC。细节见上面「专题：gRPC vs NATS」。

#### 3. P0：数据一致性分层（岗位 MySQL/Mongo/Redis + 缓存一致性）

**岗位场景：** 订单强一致、会话态最终一致、热数据走缓存。

**你项目同构方案：** 钱强一致（PG 事务） / 局内进度最终一致（内存 + write-behind） / 配置走本地+Redis。

| 岗位说法 | 你项目对应 | 证据位置 |
|---|---|---|
| 强一致写 | Spin 余额条件更新 + 账本 + 幂等同事务 | `internal/asset/settlement.go` |
| 最终一致 / 异步写 | 房间态进写队列，按玩家分片合并落盘 | `nodes/game/db/dynamodb/room_data_manager.go` + `write_behind_queue` |
| 缓存策略 | 配置本地缓存；热路径少查库 | `config_cache`、Spin 热路径设计 |
| 条件写防竞态 | `UPDATE money WHERE money >= bet` | `settlement.go` |

**一句话翻译：** 客服里「会话进度可短暂不一致，账单/订单不能错」= 游戏里「房间进度可 write-behind，金币必须事务」。

#### 4. P1：高并发热路径 + 性能优化（岗位性能优化/稳定性）

**岗位场景：** 大促/高峰消息洪峰下，接口还要稳、还要快。

| 岗位说法 | 你项目对应 |
|---|---|
| 按用户串行防乱序 | per-player Actor：同用户串行、不同用户并行 |
| 热路径减负 | 关键同步、副作用异步（Outbox / afterSpin） |
| 真实优化数字 | Node 项目 Spin **300ms → 80ms**（并行预取+两级缓存+分片+异步） |
| 并发隐患治理 | CallWait 超时死锁、`Actor.state` race、健康检查 map 崩溃 |

#### 5. P1：线上问题定位（岗位日志/DB/Redis/MQ 排查）

| 岗位说法 | 你项目对应 |
|---|---|
| 线上排障 | pprof、runtime 监控、告警自动 dump profile |
| 竞态/死锁定位 | `-race` + 回归测试（CallWait、NodeHealthChecker） |
| MQ 问题排查 | NATS 连接池重复消息、RequestSync 超时双关等问题文档 |

#### 6. P2：AI 辅助研发（JD 明确写了 Cursor 等）

你已有真实实践：用 Cursor 辅助改并发代码，但关键路径（资金/幂等）必须人审 + 测试/`-race`。这点直接对齐任职要求 9/10。

### 8.3 重合度总表（面试时心里有数）

| 岗位关键词 | 重合度 | 你怎么讲 |
|---|---|---|
| Outbox / 幂等 / 重试 / ACK | **极高** | 直接讲 Spin Outbox 全套，这是最强武器 |
| WebSocket / 在线 / 推送 / 路由 | **高** | Gate + Session + 推送链路 |
| Redis / 缓存一致性 | **高** | 热数据、写回、配置缓存 |
| MySQL/PG 设计与事务 | **高** | 结算三表 + 条件更新 + 唯一键 |
| Go 并发与稳定性 | **高** | Actor、CallWait、race 修复 |
| Kafka | **中（同构）** | 讲 JetStream/SQS 等价能力 + Kafka 差异 |

### 8.4 面试时优先打出的 4 张牌（按岗位胃口排序）

1. **Outbox + 幂等 + 可靠投递**（对齐职责5，最值钱）——直接用「难点 4」
2. **WebSocket 长连接 + 会话路由 + 在线状态**（对齐职责4/7）——Gate / Session / 推送链路
3. **强一致 vs 最终一致分层**（对齐职责6）——钱走事务，进度走 write-behind
4. **线上并发问题真实排查**（对齐职责10）——CallWait 死锁、map 崩溃、`-race` 验证

**客服场景翻译口诀（说的时候把游戏词换成岗位词）：**

| 游戏侧说法 | 换成客服 SaaS 说法 |
|---|---|
| 玩家 / UID | 坐席 / 会话 / 用户 |
| Gate 长连接 | 客服端 WebSocket 在线通道 |
| 粘性路由到某个 Game 节点 | 会话粘滞到某个客服节点 |
| Spin 扣钱强一致 | 订单/账单状态不能错 |
| 房间进度 write-behind | 会话进度、草稿、已读状态可最终一致 |
| Outbox → JetStream → 活动节点 | 消息落库 → Kafka → 推送/工单/统计 |
| requestId 幂等回放 | 客户端重试同一条客服消息不重复入库 |
