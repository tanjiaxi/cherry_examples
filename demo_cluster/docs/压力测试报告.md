# Cherry 框架压力测试报告

## 一、测试环境

### 1.1 硬件配置
- **压测客户端**: macOS (本地机器)
- **服务端**: Ubuntu 10.10.10.251
- **数据库**: PostgreSQL (同服务器)
- **网络延迟**: ping ~5ms

### 1.2 软件配置
- **框架**: Cherry Game Framework
- **协议**: WebSocket + Pomelo 协议
- **序列化**: Protobuf
- **数据库ORM**: GORM

### 1.3 测试工具
- 自研压测客户端: `demo_cluster/robot_client/main.go`
- 系统监控: gopsutil (CPU/内存)
- 服务端监控: pprof (Goroutine数量)

## 三、测试流程

### 3.1 单个机器人完整流程

```
GetToken (HTTP) → ConnectWS → UserLogin → PlayerSelect → ActorCreate → ActorEnter → ActorEnterMachine → ActorMachine → ActorSpin
```

| 步骤 | 协议 | 说明 |
|------|------|------|
| GetToken | HTTP GET | 从 Web 节点获取登录 Token |
| ConnectWS | WebSocket | 连接 Gate 节点 (含 Pomelo 握手) |
| UserLogin | Pomelo Request | 用户登录到指定游戏服 |
| PlayerSelect | Pomelo Request | 查询玩家列表 |
| ActorCreate | Pomelo Request | 创建角色 (如果不存在) |
| ActorEnter | Pomelo Request | 角色进入游戏 |
| ActorEnterMachine | Pomelo Request | 进入老虎机机台 |
| ActorMachine | Pomelo Request | 获取机台信息 |
| ActorSpin | Pomelo Request | 执行 Spin 操作 |

### 3.2 批量压测流程

1. **分批启动**: 每批 200 个机器人，间隔 100ms
2. **并发执行**: 同批机器人并发执行完整登录流程
3. **错误监控**: 错误率超过 10% 时停止
4. **持续 Spin**: 登录完成后持续发送 Spin 请求
5. **断开连接**: 测试结束后断开所有连接

## 五、发现的性能瓶颈

### 5.1 客户端端口耗尽

**现象**:
```
dial tcp 10.10.10.251:10010: connect: can't assign requested address
```

**原因**: macOS 默认临时端口范围 49152-65535，只有约 16000 个端口

**解决方案**:
```bash
sudo sysctl -w net.inet.ip.portrange.first=10000
sudo sysctl -w net.inet.ip.portrange.last=65535
# 扩展到约 55000 个端口
```

### 5.2 WebSocket 连接超时

**现象**:
```
dial tcp 10.10.10.251:10010: connect: operation timed out
```

**原因**: 
- 服务端 accept 队列满
- 服务端处理新连接速度跟不上

**排查方向**:
- 检查服务端 `net.core.somaxconn` 配置
- 检查服务端 Goroutine 数量是否暴涨

### 5.3 HTTP 请求超时

**现象**:
```
context deadline exceeded (Client.Timeout exceeded while awaiting headers)
```

**原因**: Web 节点处理能力不足，HTTP 请求排队

**解决方案**:
- 增加 Web 节点实例
- 优化 GetToken 接口性能

### 5.4 WebSocket 连接耗时过长 (200ms+)

**现象**: ping 只有 5ms，但 ConnectWS 需要 200-300ms

**分析**:
WebSocket 连接包含多个阶段：
```
ConnectWS 总耗时 = TCP握手 + HTTP Upgrade + Pomelo Handshake
                 ≈ 5ms    + 5ms         + 190ms (异常!)
```

**已添加的诊断日志**:
```go
// 客户端 - client.go
dialStart := time.Now()
conn, _, err := dialer.Dial(u.String(), nil)
dialElapsed := time.Since(dialStart)
if dialElapsed > 50*time.Millisecond {
    clog.Warnf("[%s] WS Dial slow: %v", p.TagName, dialElapsed)
}

// 服务端 - command.go
func handshakeCommand(agent *Agent, _ *ppacket.Packet) {
    start := time.Now()
    // ... 处理握手
    elapsed := time.Since(start)
    if elapsed > 10*time.Millisecond {
        clog.Warnf("[sid = %s] Handshake slow: %v", agent.SID(), elapsed)
    }
}
```

**可能原因**:
1. 服务端 accept 后到处理 handshake 之间有延迟
2. 客户端等待服务端 handshake 响应时网络延迟
3. 高并发时服务端处理队列积压

### 5.5 数据库连接池等待

**现象**: GORM 显示 SQL 耗时 20ms+，但 PostgreSQL 慢查询日志只有 1 条 10ms

**原因**: GORM 计时包含连接池等待时间

**分析**:
```
GORM 耗时 = 连接池等待 + SQL 执行
20ms     = 10ms       + 10ms
```

**解决方案**:
```go
// 增加连接池配置
db.SetMaxIdleConns(200)      // 空闲连接数
db.SetMaxOpenConns(300)      // 最大连接数
db.SetConnMaxLifetime(time.Hour)  // 连接最大生命周期
db.SetConnMaxIdleTime(10*time.Minute) // 空闲连接最大时间
```

## 六、性能瓶颈定位方法

### 6.1 区分客户端 vs 服务端瓶颈

| 现象 | 可能原因 |
|------|----------|
| 客户端 CPU 100% | 客户端瓶颈 |
| 服务端 Goroutine 暴涨 | 服务端瓶颈 |
| 延迟随并发线性增长 | 服务端处理能力不足 |
| 大量连接错误 | 网络或系统配置问题 |

### 6.2 使用 pprof 分析

```bash
# CPU 分析
go tool pprof http://127.0.0.1:6060/debug/pprof/profile?seconds=30

# 内存分析
go tool pprof http://127.0.0.1:6060/debug/pprof/heap

# Goroutine 分析
go tool pprof http://127.0.0.1:6060/debug/pprof/goroutine
```

### 6.3 分阶段测试

1. **纯连接测试**: 只测试 ConnectWS，不发送业务请求
2. **纯消息测试**: 复用已有连接，只测试消息吞吐
3. **混合测试**: 完整业务流程

## 七、优化建议

### 7.1 系统配置优化

```bash
# Linux 服务端
sysctl -w net.core.somaxconn=65535
sysctl -w net.ipv4.tcp_max_syn_backlog=65535
sysctl -w fs.file-max=1000000

# macOS 客户端
sysctl -w net.inet.ip.portrange.first=10000
```

### 7.2 数据库优化

- 增加连接池大小
- 添加必要索引
- 使用连接池预热

### 7.3 框架优化方向

- Actor 消息队列监控
- 连接处理异步化
- 批量消息处理
