## 二、常见面试问题

### 2.1 架构设计类

**Q1: 如何设计一个支持10万在线的游戏服务器?**

**答题思路**:
1. 整体架构设计
   - 分层架构: Web/Gate/Game/Center
   - 无状态设计,易于水平扩展
   - 服务发现,动态路由

2. 并发模型选择
   - Actor模型,无锁并发
   - 每个玩家独立Actor
   - 消息队列化处理

3. 数据存储
   - PostgreSQL主从复制
   - Redis缓存热数据
   - 分库分表策略

4. 性能优化
   - 连接池管理
   - 批量操作
   - 对象池复用
   - 异步处理

5. 高可用保证
   - 多节点部署
   - 故障自动转移
   - 数据备份
   - 监控告警

**Q2: Actor模型相比传统线程模型有什么优势?**

**答**:
1. **无锁设计**
   - 传统: 共享内存+锁,容易死锁
   - Actor: 消息传递,无共享状态

2. **易于理解**
   - 传统: 复杂的锁逻辑
   - Actor: 单线程处理,逻辑清晰

3. **天然分布式**
   - 传统: 难以跨机器
   - Actor: 本地/远程调用一致

4. **容错性好**
   - 传统: 一个线程崩溃影响全局
   - Actor: 隔离性好,单个Actor崩溃不影响其他

5. **性能优势**
   - 传统: 锁竞争成为瓶颈
   - Actor: 无锁,性能线性扩展

**示例代码**:
```go
// 传统模型
type Player struct {
    mu   sync.Mutex
    coin int64
}

func (p *Player) AddCoin(amount int64) {
    p.mu.Lock()
    defer p.mu.Unlock()
    p.coin += amount  // 需要加锁
}

// Actor模型
type ActorPlayer struct {
    coin int64
}

func (a *ActorPlayer) OnReceive(msg Message) {
    switch msg.Type {
    case "add_coin":
        a.coin += msg.Amount  // 无需加锁
    }
}
```

### 2.2 性能优化类

**Q3: 如何定位和解决性能瓶颈?**

**答题思路**:

1. **监控指标**
   - 响应时间、QPS、错误率
   - CPU、内存、网络、磁盘
   - 数据库连接数、慢查询

2. **性能分析工具**
   - pprof: CPU/内存分析
   - trace: 并发分析
   - 数据库EXPLAIN: 查询分析

3. **常见瓶颈**
   - 数据库: 慢查询、连接池耗尽
   - 网络: 连接数过多、带宽不足
   - 内存: 泄漏、GC频繁
   - CPU: 计算密集、锁竞争

4. **优化方法**
   - 数据库: 索引、查询优化、读写分离
   - 缓存: 多级缓存、预加载
   - 异步: 消息队列、协程池
   - 批量: 批量读写、合并请求

**实际案例**:
```
问题: 数据库连接池耗尽
现象: 响应时间5000ms+, 错误率5%
排查: 
  1. 查看连接数: 100/100 (满了)
  2. 查看慢查询: 大量SELECT未释放
  3. 查看代码: 忘记Close连接
优化:
  1. 使用GORM自动管理连接
  2. 降低MaxOpenConns: 100→50
  3. 增加MaxIdleConns: 10→25
  4. 批量操作减少连接占用
效果: 响应时间50ms, 错误率0.01%
```

**Q4: 如何保证数据一致性?**

**答**:
1. **Actor单线程**
   - 单个玩家操作串行化
   - 内存状态天然一致

2. **数据库事务**
   - ACID保证
   - 乐观锁/悲观锁

3. **分布式锁**
   - Redis实现
   - 跨节点互斥

4. **最终一致性**
   - 非关键数据异步更新
   - 补偿机制

**代码示例**:
```go
// 方案1: Actor保证
func (a *ActorPlayer) handleSpin(req *SpinRequest) {
    // 单线程处理,天然一致
    a.Coin -= req.BetAmount
    result := a.calculateResult()
    a.Coin += result.WinAmount
}

// 方案2: 数据库事务

    return db.Transaction(func(tx *gorm.DB) error {
        tx.Model(&Player{}).Update("coin", a.Coin)
        tx.Create(&SpinHistory{...})

// 方案3: 分布式锁
func (a *ActorPlayer) transferCoin(toUserId int64, amount int64) error {

   - 查看错误日志

3. **指标对比**
   - 对比正常时期
   - 找出异常指标
   - 定位问题模块

4. **快速止损**
   - 回滚版本
   - 降级功能
   - 扩容资源

5. **根因分析**
   - 复现问题
   - 代码审查
   - 修复验证

```

### 2.4 业务理解类

2. **RTP控制**
   - 设定目标RTP(如95%)
   - 长期统计接近目标值

3. **服务器端计算**
   - 客户端不可篡改
   - 所有逻辑服务器执行
   - 结果可审计

4. **审计日志**
   - 记录每次Spin
   - 可追溯验证
   - 定期第三方审计

5. **防作弊机制**

   - 频率限制
   - 行为分析
