# 分布式系统日志与链路追踪最佳实践

## 一、日志存储策略对比

### 1.1 方案对比

| 方案 | 优点 | 缺点 | 适用场景 |
|-----|------|------|---------|
| **单文件集中** | ❌ 不推荐 | 文件锁竞争、写入瓶颈 | 仅单机测试 |
| **按节点分文件** | ✅ 简单、无竞争 | ❌ 难以追踪跨节点调用 | 小规模集群 |
| **集中式日志系统** | ✅ 易于查询、链路追踪 | 需要额外组件 | **生产环境推荐** |


- ❌ 需要手动在多个文件中查找日志
- ❌ 跨节点调用链难以追踪

### 3.2 阶段二：引入 TraceID（核心改进）

#### TraceID 设计

**什么是 TraceID？**
- 全局唯一的请求标识符
- 贯穿整个调用链
- 用于关联分布式系统中的所有日志

**生成规则：**
```go
// 在请求入口生成 TraceID
func GenerateTraceID() string {
    // 格式：时间戳-节点ID-序列号
    return fmt.Sprintf("%d-%s-%d", 
        time.Now().Unix(),
        nodeID,
        atomic.AddUint64(&seq, 1),
    )
    // 示例：1704888735-gate-001-12345
}
```

#### 在 Cherry 框架中实现 TraceID

**步骤 1：扩展 Message 结构体**
```go
// 3rd/cherry-game/cherry/facade/message.go
type Message struct {
    // ... 现有字段
    
    // 链路追踪字段
    TraceID      string  `json:"trace_id"`       // 全局追踪 ID
    SpanID       string  `json:"span_id"`        // 当前 Span ID
    ParentSpanID string  `json:"parent_span_id"` // 父 Span ID
}
```

**步骤 2：在 Gateway 入口生成 TraceID**
```go
// demo_cluster/nodes/gate/route.go
func onPomeloDataRoute(agent, route, msg) {
    // 1. 生成全局 TraceID
    traceID := GenerateTraceID()
    spanID := GenerateSpanID()
    
    // 2. 构造 Message
    message := BuildMessage(msg)
    message.TraceID = traceID
    message.SpanID = spanID
    message.ParentSpanID = ""  // 入口没有父 Span
    
    // 3. 记录日志（带上 TraceID）
    clog.WithFields(map[string]interface{}{
        "trace_id": traceID,
        "span_id": spanID,
        "uid": session.Uid,
        "route": msg.Route,
    }).Infof("[GATE-IN] route=%s, mid=%d", msg.Route, msg.ID)
    
    // 4. 转发消息（TraceID 会自动传递）
    LocalDataRoute(agent, session, route, msg, targetPath)
}
```

**步骤 3：RPC 调用时传递 TraceID**
```go
// 3rd/cherry-game/cherry/net/actor/invoke.go
func InvokeRemoteFunc(app, fi, m) {
    // 1. 生成新的 SpanID
    newSpanID := GenerateSpanID()
    
    // 2. 记录 RPC 调用日志（传递 TraceID）
    clog.WithFields(map[string]interface{}{
        "trace_id": m.TraceID,           // ← 继承 TraceID
        "span_id": newSpanID,            // ← 新的 SpanID
        "parent_span_id": m.SpanID,      // ← 记录父 SpanID
        "source": m.Source,
        "target": m.Target,
    }).Infof("[BIZ-RPC-OUT]")
    
    // 3. 构造 RPC 消息（包含 TraceID）
    packet := &ClusterPacket{
        TraceID:      m.TraceID,
        SpanID:       newSpanID,
        ParentSpanID: m.SpanID,
        // ... 其他字段
    }
}
```

**步骤 4：接收端记录日志**
```go
// Center 节点接收到 RPC 请求
func InvokeRemoteFunc(app, fi, m) {
    clog.WithFields(map[string]interface{}{
        "trace_id": m.TraceID,           // ← 相同的 TraceID
        "span_id": m.SpanID,
        "parent_span_id": m.ParentSpanID,
    }).Infof("[BIZ-RPC-IN]")
}
```

### 3.3 阶段三：集中式日志系统（生产环境）

#### ELK Stack 架构

**组件说明：**
- **Filebeat**：轻量级日志采集器，部署在每个节点
- **Logstash/Fluentd**：日志解析和转发
- **Elasticsearch**：日志存储和索引
- **Kibana**：可视化查询界面

#### 部署步骤

**1. 安装 Filebeat（每个节点）**
```yaml
# filebeat.yml
filebeat.inputs:
  - type: log
    enabled: true
    paths:
      - /path/to/demo_cluster/nodes/logs/*.log
    json.keys_under_root: true  # JSON 日志解析
    json.add_error_key: true
    fields:
      cluster: cherry-game
      
output.logstash:
  hosts: ["logstash:5044"]
```

**2. 安装 Logstash**
```ruby
# logstash.conf
input {
  beats {
    port => 5044
  }
}

filter {
  # 解析 JSON 日志
  json {
    source => "message"
  }
  
  # 添加时间戳索引
  date {
    match => ["timestamp", "ISO8601"]
  }
}

output {
  elasticsearch {
    hosts => ["elasticsearch:9200"]
    index => "cherry-game-%{+YYYY.MM.dd}"
  }
}
```

**3. Kibana 查询界面**

**查询示例：**
```

# 查询某个用户的所有请求

# 查询慢请求（响应时间 > 500ms）

# 查询错误日志

```

**可视化效果：**

## 四、最佳实践总结

### 4.1 日志分层策略

| 层级 | 日志前缀 | 包含信息 | 目的 |
|-----|---------|---------|------|
| **Gateway 层** | `[GATE-IN/OUT]` | uid, sid, mid, route | 客户端请求追踪 |
| **业务层** | `[BIZ-IN]` | session, args | 本地业务调用 |
| **RPC 层** | `[BIZ-RPC-IN/OUT]` | source, target, code | 跨节点调用 |
| **数据层** | `[DB-QUERY]` | table, sql, duration | 数据库操作 |

### 4.2 TraceID 传递规则

```
规则 1：在请求入口生成 TraceID
规则 2：所有日志必须包含 TraceID
规则 3：跨节点调用时传递 TraceID（通过 Message Header）
规则 4：每个 RPC 调用生成新的 SpanID
规则 5：SpanID 记录父子关系（ParentSpanID）
```

### 4.3 日志格式规范

**强制字段：**
```json
{
  "timestamp": "ISO8601 格式",
  "level": "INFO/WARN/ERROR",
  "node_id": "节点 ID",
  "trace_id": "全局追踪 ID",
  "span_id": "当前 Span ID",
  "message": "日志内容"
}
```

**推荐字段：**
```json
{
  "uid": "用户 ID",
  "sid": "会话 ID",
  "source": "来源节点",
  "target": "目标节点",
  "duration": "耗时（毫秒）",
  "code": "响应码"
}
```

### 4.4 性能优化建议

**1. 使用异步日志**
```go
// 使用 zap 的异步日志
logger, _ := zap.NewProduction(
    zap.AddCaller(),
    zap.AddStacktrace(zap.ErrorLevel),
    zap.WrapCore(func(core zapcore.Core) zapcore.Core {
        // 使用 BufferedWriteSyncer 批量写入
        return zapcore.NewCore(
            zapcore.NewJSONEncoder(config),
            zapcore.AddSync(&BufferedWriteSyncer{
                WS: zapcore.AddSync(file),
            }),
            level,
        )
    }),
)
```

**2. 日志分级采样**
```go
// 高频日志降级采样
if rand.Float64() < 0.1 {  // 只记录 10%
    clog.Debugf("[HIGH-FREQ] ...")
}
```

**3. 日志轮转**
```json
{
  "max_size": 100,      // 单文件最大 100MB
  "max_backups": 10,    // 保留 10 个备份
  "max_age": 30,        // 保留 30 天
  "compress": true      // 压缩旧日志
}
```

## 五、不同规模的推荐方案

### 5.1 小规模集群（< 10 节点）

**方案：按节点分文件 + TraceID + grep/jq 查询**

```bash
# 查询工具脚本
#!/bin/bash
# trace.sh - 追踪完整调用链

TRACE_ID=$1
LOG_DIR="./nodes/logs"

echo "Searching for trace_id: $TRACE_ID"
cat $LOG_DIR/*.log | \
  jq "select(.trace_id == \"$TRACE_ID\")" | \
  jq -s 'sort_by(.timestamp)' | \
  jq -r '.[] | "\(.timestamp) [\(.node_id)] \(.message)"'
```

**使用：**
```bash
./trace.sh trace-abc123
```

### 5.2 中等规模（10-50 节点）

**方案：按节点分文件 + Filebeat + ELK**

**优点：**
- ✅ 可视化查询（Kibana）
- ✅ 支持复杂查询
- ✅ 实时监控和告警

### 5.3 大规模（> 50 节点）

**方案：OpenTelemetry + Jaeger/Zipkin**

```go
import (
    "go.opentelemetry.io/otel"
    "go.opentelemetry.io/otel/trace"
)

// 在 Actor 调用时创建 Span
func InvokeRemoteFunc(app, fi, m) {
    ctx := context.Background()
    tracer := otel.Tracer("cherry-framework")
    
    // 创建 Span
    ctx, span := tracer.Start(ctx, "RPC."+m.FuncName,
        trace.WithAttributes(
            attribute.String("source", m.Source),
            attribute.String("target", m.Target),
        ),
    )
    defer span.End()
    
    // 业务逻辑
    result := fi.Value.Call(values)
    
    // 记录结果
    span.SetAttributes(attribute.Int("code", result.Code))
}
```

**可视化效果（Jaeger）：**
```
gate.user.login (55ms)
  ├─ gate.rpc.call (50ms)
  │   └─ center.account.devLogin (45ms)
  │       └─ db.query.user (20ms)
  └─ gate.response (5ms)
```

## 七、总结

### ✅ 推荐方案

| 阶段 | 方案 | 实施成本 | 查询效率 |
|-----|------|---------|---------|
| **初期** | 按节点分文件 + TraceID | 低 | 中 |
| **中期** | ELK Stack | 中 | 高 |
| **成熟期** | OpenTelemetry + Jaeger | 高 | 极高 |

### 🎯 关键要点

1. **永远不要用单文件**：会产生文件锁竞争
2. **必须有 TraceID**：这是链路追踪的核心
3. **日志必须结构化**：使用 JSON 格式
4. **考虑性能影响**：使用异步日志、采样
5. **逐步演进**：从简单方案开始，逐步升级
